## ADDED Requirements

### Requirement: A description is YAML, validated against its schema

A description SHALL be a `*.description.yaml` file, read under YAML 1.2's core
schema and validated against `src/describe/description.schema.json` by the one
loader that `npm run describe`, the help build, the tests and the research
tools share. A description that fails SHALL fail the load, naming the file and
the field. Nothing the app bundles SHALL import the loader or its parsers.

#### Scenario: A formula is read as a map

- **WHEN** a technique's `conclude` is written unquoted on its own line as
  `forall c in cells: known(c)`, which YAML reads as a map
- **THEN** the load fails, naming the file and `/techniques/<n>/conclude`
  as not a string

#### Scenario: A word YAML 1.1 reads as a boolean

- **WHEN** a prose or formula field is the word `no`
- **THEN** it loads as the string `no`

## MODIFIED Requirements

### Requirement: Nothing is generated into the source tree

Nothing the build reads SHALL be generated by the build: the game catalog is
committed TypeScript source (`src/puzzle/catalog-data.ts`), the per-puzzle
icons are a committed snapshot, and the help pages are committed markdown and
descriptions. There SHALL be no asset build step. A module compiled from a
description (`*.compiled.ts`) SHALL be committed beside it, and a test in the
gate SHALL compile every description again and fail where the committed module
differs.

#### Scenario: No artifact is generated into the source tree

- **WHEN** the repository is inspected after a build
- **THEN** `src/assets/` holds only committed files
- **AND** `.gitignore` carries no rule for a generated directory under `src/`

#### Scenario: A description edited without compiling fails the gate

- **WHEN** a technique in a `*.description.yaml` is edited and
  `npm run describe` is not run
- **THEN** the gate fails, naming the description whose module is stale
